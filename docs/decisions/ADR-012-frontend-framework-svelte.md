# ADR-012: 프론트 프레임워크 — Svelte + Vite

## 상태
제안됨 (2026-11-10). 프론트 담당 초안이며, PR 리뷰에서 팀이 합의하면 "채택됨"으로 바꾼다.

## 관련 드라이버
D1(정확한 위치에 가리기), D2(풀이 중 정답이 우연히 보이면 안 된다), D4(신뢰할 수 없는 PDF 글자), D7(4명, 6주) — [아키텍처 정의서 0장](../architecture.md#0-아키텍처-드라이버와-품질-목표)

## 컨텍스트

프론트 구조는 "프론트 스파이크 결과가 필요"해서 미뤄 두었다([아키텍처 9.1](../architecture.md)). #57에서 같은 화면을 두 후보로 만들어 비교했다. 코드는 `frontend/spike/vanilla/`(순수 HTML/JS)와 `frontend/spike/svelte/`(Svelte + Vite)에 있다.

두 후보 모두 같은 기능을 가진다.

- `mask` 명령 결과(`page_NNN.json` + `.webp`)와 계약 1.4 모양을 읽어 입력칸을 겹친다.
- 위치는 퍼센트, 폭과 글자 크기는 `cqw`라 창 크기가 바뀌어도 비율이 같다.
- Enter·Tab 이동, 한글 조합 보호, 가짜 채점과 결과 표시, 중복 제출 막기([채점·입력칸 3.2](../design/grading-and-overlay.md#32-입력칸-규칙-프론트)).

이후 화면은 상태가 많다. 폴링 상태와 진행률(#58), 제출 결과·정답 공개·다시 풀기(#36), 로그인·업로드·문서 목록(#35), 빈칸 끄고 켜기(#59)가 이어진다. 프레임워크는 이 화면들을 4명이 6주 안에 만들 수 있는지를 기준으로 고른다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 순수 HTML/JS | 빌드 도구·Node가 필요 없다. 파일 그대로 FastAPI가 내보낸다. 내려받는 코드가 없다 | 상태가 바뀔 때마다 DOM을 직접 고친다(결과 표시를 지우는 코드 등). 화면이 늘수록 이 코드가 흩어진다. 서버 글자를 `textContent`로 넣는 것을 사람이 매번 지켜야 한다 |
| **Svelte + Vite** | 상태(`$state`)를 바꾸면 화면이 따라 바뀐다. 화면을 컴포넌트(쪽 하나 = `Page.svelte`)로 나눈다. 텍스트 출력이 기본으로 이스케이프된다(`{@html}`을 쓰지 않는 한). 빌드 결과가 작다 | Node와 빌드 단계가 생긴다. 배포 이미지에 프론트 빌드 단계가 필요하다. 화면 갱신이 한 박자 늦게(비동기) 일어나 테스트에서 기다려야 한다 |
| Alpine.js | 빌드 없이 HTML 속성으로 상태를 묶는다 | 화면이 커지면 HTML 속성 안의 코드가 길어진다. 컴포넌트 나누기가 약하다. 이번 스파이크에서는 만들지 않았다 |
| React·Vue | 자료와 사용자가 가장 많다 | 이 규모에 비해 무겁다. 런타임이 Svelte보다 크다. 이번 스파이크에서는 만들지 않았다 |

### 스파이크 측정 (2026-11-10)

| 항목 | 순수 HTML/JS | Svelte + Vite |
|---|---|---|
| 입력칸 위치 오차(창 폭 1100·768·343px) | 0.01px 이하 | 0.01px 이하 |
| 한글 조합 시나리오 7개(조합 중 Enter·Tab, 확정 직후 Enter, keyup 없음, 마지막 칸, 연타) | 모두 의도대로 | 모두 의도대로 |
| 직접 쓴 코드 | `app.js` 294줄(데이터 읽기·가짜 채점·한글 조합 포함) | 화면 140줄(`App` 84 + `Page` 56) + 데이터·가짜 채점 103 + 한글 조합 23 + 설정·진입점 47 |
| 브라우저가 받는 JS | 12KB(주석 포함 원본, 줄이지 않음) | 46KB(줄인 결과, gzip 18.5KB) |
| 빌드 | 없음 | `npm run build` 0.2초, `node_modules` 44MB(커밋 안 함) |
| FastAPI `StaticFiles` 제공 | 확인함 | `dist/` 확인함(`base: "./"`) |

한글 조합 처리는 두 후보가 같은 코드다. 프레임워크가 도와주는 부분이 없어서, 어느 쪽을 골라도 직접 만들어야 한다.

## 결정

Svelte + Vite를 쓴다.

스파이크 한 화면에서는 코드 양 차이가 작다. 차이는 앞으로 늘어날 화면의 상태 처리에서 난다. 순수 HTML/JS는 결과 표시·지우기·버튼 잠금을 DOM을 직접 고쳐 맞췄다. Svelte는 같은 일을 상태 값 하나로 한다. 텍스트 이스케이프가 기본이라 D4(PDF에서 나온 글자를 HTML로 해석하지 않기)를 지키기도 쉽다. 빌드 단계와 Node가 생기는 비용은 있지만, 결과물은 정적 파일이라 ADR-007의 "한 주소" 구조는 그대로다.

## 한글 조합(IME) 처리 규칙

프레임워크와 상관없이 입력칸에 적용하는 규칙이다. 두 후보가 같은 코드(`frontend/spike/svelte/src/ime.js`, `frontend/spike/vanilla/app.js`)를 쓴다. 한글은 `ㅎ → 하 → 한`처럼 조합을 거치는데, 조합 중에 누른 Enter·Tab이 칸 이동으로도 처리되면 마지막 글자가 다음 칸으로 넘어가거나 사라지고, 한 번 눌렀는데 두 칸 이동하거나 두 번 제출된다.

1. **조합 구간 기록.** 문서 전체에서 `compositionstart`가 오면 "조합 중"으로, `compositionend`가 오면 "조합 끝"으로 표시한다.
2. **조합 중 Enter·Tab 막기.** 아래 중 하나라도 맞으면 Enter·Tab의 `keydown`을 `preventDefault()`하고 이동·제출을 하지 않는다. 키는 글자 확정에만 쓰인다.
   - `event.isComposing`이 참
   - `event.keyCode === 229`(IME가 처리 중인 키. 오래된 브라우저 대비)
   - 1번에서 기록한 "조합 중"
3. **조합 직후 Enter·Tab 막기.** 일부 브라우저는 조합을 끝낸 Enter를 `compositionend` 직후 `isComposing`이 거짓인 보통 Enter로 한 번 더 보낸다. 그래서 `compositionend` 뒤에는 그 키를 놓을 때(`keyup`)까지 Enter·Tab을 계속 막는다. `keyup`이 오지 않는 경우(창 전환 등)를 위해 100ms가 지나면 막기를 푼다.
4. **결과.** 조합 중 Enter는 글자만 확정한다. 다음 칸 이동은 확정 뒤 Enter를 한 번 더 눌러야 한다. 마지막 칸의 제출도 같은 규칙을 따르고, 제출 요청 중에는 버튼과 Enter 제출을 잠가 중복 제출을 막는다.

스파이크에서는 브라우저 이벤트 순서를 흉내 낸 시나리오 7개로 확인했다. 실제 한글 입력기(Windows 한국어 IME 등) 확인은 PR 리뷰 전에 사람이 직접 하고 결과를 PR에 남긴다.

## 결과

- 프론트 코드는 `frontend/`에 Svelte 5 + Vite로 둔다. 빌드 결과는 `frontend/dist/`로 제안한다. 위치는 #48(FastAPI 뼈대) 담당과 맞춘다.
- `node_modules/`와 `dist/`는 커밋하지 않는다. 패키지 버전은 `package.json`에 정확한 버전으로 고정하고 `package-lock.json`을 커밋한다.
- 배포 이미지를 만들 때 Node로 프론트를 빌드하는 단계가 필요하다(#60 배포 담당과 맞춘다).
- 화면 코드는 API를 직접 부르지 않고 통신 모듈(`api.js`) 하나를 거친다. 서버가 없을 때는 Mock 응답으로 먼저 만든다.
- 한글 조합 보호는 위 "한글 조합(IME) 처리 규칙"대로 스파이크의 `ime.js`를 옮겨 쓴다.

## 재검토 조건

- 팀에 Svelte를 아는 사람이 없어 학습 비용이 크다고 판단되면, 순수 HTML/JS(스파이크 코드)로 돌아간다.
- 배포에서 Node 빌드 단계를 둘 수 없으면 순수 HTML/JS나 Alpine.js를 다시 검토한다.
