# ADR-012: 워커 재시작 즉시 재배달은 실행 횟수 상한과 함께 도입한다

## 상태
제안됨 (2026-11-12). [ADR-001](ADR-001-task-queue-taskiq.md)(Taskiq + RedisStreamBroker)을 보완한다. 대체하지 않는다.

## 관련 드라이버
- **D3**(작업이 사라지면 안 된다): 사라지지 않는 것만으로는 부족하다. 처리 중에 죽은 작업이 15분 넘게 멈춰 있으면 사용자에게는 실패와 같다.

## 컨텍스트

### 재배달 실험 [확인]

#49에서 처리 중인 워커를 강제 종료하는 실험을 했다(2026-11-12, taskiq 0.13.0, taskiq-redis 1.2.4, `scripts/redelivery_experiment.py`, `idle_timeout` 60초로 줄여 실행).

| 실험 | 결과 |
|---|---|
| 정상 처리 | 실행이 끝난 뒤 ack. 기본 ack 시점은 `when_saved`(`taskiq/receiver/receiver.py`). ADR-001의 미확인 항목("ack를 실행 후에 보내는가")은 **실행 후**로 확인됨 |
| 처리 중 워커 강제 종료 → 재시작 | `idle_timeout`(60초)을 넘겨 105초가 지나도 회수되지 않음. 메시지는 죽은 컨슈머 소유로 대기 목록(PEL)에 남음 |
| 이어서 새 작업 하나 등록 | 새 작업을 받은 직후(9ms) 멈춘 작업이 같은 작업 ID로 회수되어 실행됨 |
| Redis 강제 종료(`docker kill`) | 처리 전 작업이 AOF로 복구됨 |
| 워커가 모르는 작업 이름 | 경고 로그만 남기고 ack되어 사라짐 |

원인은 taskiq-redis `RedisStreamBroker.listen()`이다.

1. 컨슈머 이름이 기본으로 재시작마다 새 uuid다. 다시 뜬 워커는 이전 자신의 대기 목록을 모른다.
2. 새 메시지만 읽는다(`XREADGROUP` ID `>`). 새 메시지가 없으면 반복 처음으로 돌아가, 오래 멈춘 메시지를 가져오는 `XAUTOCLAIM`까지 가지 않는다.

그래서 처리 중에 죽은 작업은 **`idle_timeout`(15분)이 지난 뒤 새 메시지가 하나 들어올 때** 회수된다. 조용한 시간에는 정리 작업([ADR-011](ADR-011-periodic-jobs-scheduler.md))의 매시 정각 쪽지가 그 계기가 되어 최악 약 75분이 걸린다. 스케줄러도 멈춰 있으면 다음 업로드까지 기다린다. ADR-011 컨텍스트 표의 "`idle_timeout` 뒤 다른 워커에게 다시 배달"은 이 조건을 빠뜨렸다.

`idle_timeout`을 줄일 수는 없다. 작업 제한 시간(8분)보다 짧으면 살아서 처리 중인 작업이 다른 워커로 넘어가 두 번 실행된다([신뢰성 설계](../design/reliability.md) 2절).

### 워커가 죽는 실제 경우

메모리 초과(큰 PDF), 배포 때 컨테이너 재시작(`docker stop`은 10초 뒤 강제 종료), 기기 재부팅이다. 셋 다 **같은 워커가 곧 다시 뜬다.** 다시 뜬 워커는 이전의 자신이 확실히 죽었다는 것을 안다. 15분을 기다릴 이유가 없다.

단, 메모리 초과는 같은 PDF가 다시 워커를 죽인다(독 메시지).

## 검토한 선택지

| 선택지 | 결과 | 결론 |
|---|---|---|
| ① 그대로 둠 | 재시작 복구 15~75분. 독 PDF는 그 간격으로 끝없이 반복 | 탈락 |
| ② `idle_timeout` 단축 | 작업 제한 시간보다 짧으면 살아 있는 작업을 두 번 실행 | 탈락 |
| ③ 컨슈머 이름만 고정 | `>`는 자기 대기 목록을 돌려주지 않는다. 같은 이름으로 `>`를 다시 읽으면 빈 응답, `0`으로 읽어야 돌려받음 [확인, redis-cli] | 효과 없음 |
| ④ 이름 고정 + 시작할 때 `0`으로 한 번 읽기, 상한 없음 | 재시작 복구 수 초. 그러나 독 PDF는 수 초마다 워커를 죽이는 크래시 루프가 되고, 그동안 다른 작업도 멈춤 | 탈락 |
| ⑤ ④ + Redis 배달 횟수로 상한 | `0`으로 다시 읽을 때마다 `XPENDING`의 배달 횟수가 1씩 오름 [확인, redis-cli]. 하지만 실행 횟수를 Postgres 하나로 센다는 원칙([신뢰성 설계](../design/reliability.md) 3절)과 어긋나 카운터가 둘이 됨 | 탈락 |
| **⑥ ④ + Postgres `run_count` 상한** | 재시작 복구 수 초. 독 PDF는 상한(4회)에 닿으면 `failed` 기록 후 ack | **채택** |

## 결정

1. 워커는 **재시작해도 바뀌지 않고 워커끼리 겹치지 않는** 컨슈머 이름을 쓴다.
2. 브로커를 상속해, `listen()` 시작 때 한 번 `XREADGROUP` ID `0`으로 자기 대기 목록을 먼저 읽는다. 그 뒤로는 기존 동작(`>`와 `XAUTOCLAIM`)을 그대로 쓴다.
3. 작업은 시작하자마자 `run_count`를 올리고 **무거운 처리 전에 커밋**한다. 상한을 넘으면 처리하지 않고 `failed`(`processing_failed`)로 기록한 뒤 ack한다([신뢰성 설계](../design/reliability.md) 3절 2번).
4. 1~3은 **한 PR([#52](https://github.com/best-vibing/cloze/issues/52))에** 넣는다. 1·2만 먼저 머지되면 그 사이에 독 PDF 하나가 큐 전체를 멈출 수 있기 때문이다. #49에는 넣지 않는다.
5. 작업 이름은 `task_name`으로 고정한다(#49에서 적용). 기본 이름은 모듈 경로라 파일을 옮기면 바뀌고, 큐에 남은 옛 이름의 작업은 위 실험처럼 사라진다.

## 결과

- 재시작한 워커는 자기가 처리하던 작업을 수 초 안에 다시 처리한다. 독 PDF는 상한까지 몇 번 만에 `failed`가 되어 사용자가 실패를 빨리 받는다.
- `idle_timeout` + `XAUTOCLAIM` 회수는 안전망으로 남는다. 같은 이름의 워커가 다시 뜨지 않는 경우(워커 수를 줄임, 기기 고장)를 맡는다.
- 컨슈머 이름 규칙이 생긴다. 발표 때 워커를 2~3개로 늘리므로([신뢰성 설계](../design/reliability.md) 5.1) 워커마다 이름이 달라야 한다. 두 프로세스가 같은 이름을 쓰면, 한쪽이 재시작하며 다른 쪽이 처리 중인 작업까지 가져가 두 번 실행한다. 컨테이너의 hostname은 다시 만들 때 바뀌므로 그대로 쓸 수 없다.
- taskiq-redis의 `listen()` 내부에 기대므로 라이브러리를 올릴 때 재배달 실험을 다시 돌린다.
- 모르는 이름의 작업이 사라지는 경우(배포 중 API와 워커의 버전이 잠깐 다름)는 정리 작업이 멈춘 세트로 찾아 다시 등록한다(ADR-011).

## 미확인

- 워커 2개 이상에서 이름을 어떻게 나눌지: Compose 서비스를 워커마다 따로 두고 환경 변수로 이름을 줄지, `--workers N`의 프로세스 번호를 쓸 수 있는지. #52에서 정한다.
- 워커 2개 이상에서 즉시 재읽기와 `XAUTOCLAIM`이 겹칠 때의 동작.

## 재검토 조건

- taskiq-redis가 시작할 때 자기 대기 목록을 읽는 기능을 직접 제공하면 상속을 지운다.
