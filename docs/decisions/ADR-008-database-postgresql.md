# ADR-008: 데이터베이스 — PostgreSQL

## 상태
채택됨 (2026-10-28)

## 컨텍스트

작업 상태·정답·좌표·시도 기록을 오래 남길 DB가 필요하다. Redis는 작업 전달만 맡고 상태의 기준이 될 수 없다(ADR-001). 이 DB에 요구되는 것은 다음과 같다.

- `api`와 `worker`가 서로 다른 컨테이너에서 동시에 쓴다. 발표 때는 워커를 2~3개로 늘린다([신뢰성 설계](../design/reliability.md) 5.1).
- `run_count` 증가와 상태 변경이 재배달과 겹쳐도 꼬이지 않아야 한다(원자적 갱신).
- 데이터가 관계형이다. 사용자 → 문서 → 빈칸 세트 → 빈칸 → 시도로 이어지고, 소유자 확인(남의 리소스는 404, ADR-006)과 연쇄 삭제가 이 관계를 탄다.
- `migrate` 컨테이너가 Alembic으로 구조를 바꾼다(ADR-007).
- 지금은 시연 기기 하나에서 돌지만, 나중에 클라우드로 옮길 수 있어야 한다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| **PostgreSQL** | 여러 프로세스가 동시에 써도 됨. 원자적 갱신(`UPDATE … RETURNING`)과 구조 변경 트랜잭션. 클라우드 관리형(RDS, Cloud SQL, Supabase, Neon 등)이 가장 많음 | 컨테이너가 하나 늘어남 |
| SQLite | 서버가 없고 파일 하나. 원자적 갱신과 구조 변경 트랜잭션도 됨. Docker 이름 볼륨 + WAL이면 시연 규모에서는 돌아갈 가능성이 높음 | 쓰기는 한 번에 한 곳만이라 워커가 늘면 잠금 대기가 생김. 파일이라 같은 기기의 프로세스끼리만 공유할 수 있음. 클라우드에서는 디스크가 붙은 서버 한 대(또는 Turso 같은 SQLite 호환 서비스)로만 옮길 수 있고, 인스턴스를 늘리거나 디스크가 매번 지워지는 컨테이너 서비스로는 못 감 |
| 사용자마다 SQLite 하나 | 사용자끼리 쓰기가 겹치지 않음 | 아래 "사용자별 SQLite" 참고 |
| MySQL | 동시 쓰기, 관리형 많음 | 구조 변경(DDL)이 트랜잭션에 묶이지 않아 `migrate`가 중간에 실패하면 반쯤 바뀐 채로 남음 |
| MongoDB 등 문서 DB | 스키마 없이 저장 | 관계·외래키·연쇄 삭제를 앱 코드로 다시 만들어야 함 |

### 클라우드로 옮길 때

SQLite는 DB 서버가 아니라 디스크의 파일 하나라서, 그 파일이 있는 디스크에 붙은 프로세스만 쓸 수 있다.

| 클라우드 형태 | SQLite | PostgreSQL |
|---|---|---|
| 디스크가 붙은 서버 한 대(EC2, Fly 볼륨 등) | 됨. 파일을 그대로 옮김 | 됨 |
| 디스크가 매번 지워지는 컨테이너 서비스(Cloud Run 등) | 안 됨. 재시작하면 파일이 사라짐 | 됨. DB가 따로 있음 |
| 서버를 여러 대로 늘림 | 안 됨. 파일 하나를 여러 기기가 같이 쓸 수 없음 | 됨 |
| 관리형 DB(RDS, Cloud SQL, Supabase, Neon) | 없음. Turso 같은 SQLite 호환 서비스는 있으나 접속 코드가 바뀜 | 대부분 제공. 덤프·복원으로 옮김 |

### 사용자별 SQLite

DB를 사용자마다 나누면 사용자끼리 쓰기가 겹치지 않는다. 그러나 파일을 어디에 두느냐에 따라 다른 제약이 생긴다.

| 두는 곳 | 해결되는 것 | 새로 생기는 문제 |
|---|---|---|
| 사용자 브라우저(SQLite WASM 등) | 서버 DB가 필요 없음 | 정답이 사용자 기기에 있게 되어 서버 전용 정답·채점이 깨짐. 워커가 만든 결과를 서버가 사용자 DB에 쓸 수 없음. 기기를 바꾸면 기록이 사라짐. 로그인·한도·서비스 전체 Gemini 상한은 어차피 서버 DB가 필요함 |
| 서버에 사용자마다 파일 하나 | 사용자 간 잠금 대기가 없음 | 한 사용자의 세트를 여러 워커가 처리하면 같은 파일을 두고 다시 겹침. 서비스 전체 한도·정리 작업이 모든 파일을 열어야 함. 마이그레이션을 파일 수만큼 돌려야 함. 파일이 디스크에 있으니 위 클라우드 제약은 그대로 |

제약이 사라지지 않고 다른 곳으로 옮겨 갈 뿐이라 채택하지 않았다.

## 결정

PostgreSQL을 쓴다. Compose의 `postgres` 컨테이너로 띄우고, SQLAlchemy + Alembic으로 다룬다.

SQLite는 시연만 놓고 보면 가능했다. 고르지 않은 이유는 워커를 늘릴 때의 잠금 대기와 클라우드 이전 선택지가 좁아지는 것이다. 이를 피하는 비용은 컨테이너 하나뿐이다.

## 결과

- 개발할 때도 Postgres를 띄워야 한다. 단, `core`는 DB를 모르므로 CLI로 파이프라인을 검증할 때는 필요 없다([아키텍처](../architecture.md) 3.4).
- 클라우드로 옮길 때 관리형 PostgreSQL로 덤프·복원만 하면 된다.

## 재검토 조건

- 시연 기기 메모리가 부족해 컨테이너 하나도 아쉬워지면 SQLite를 다시 검토한다(워커 1개로 고정하는 조건).
