# ADR-005: 흐름 제어 — 에이전트 프레임워크(LangGraph 등)를 쓰지 않음

## 상태
채택됨 (2026-10-27)

## 컨텍스트

LangGraph는 LLM 작업 흐름을 그래프(노드·엣지·조건부 엣지)로 짜고, 체크포인터로 진행 상태를 저장하며, interrupt로 중간에 사람의 입력을 받을 수 있게 해 주는 라이브러리다. 다음 두 기능 때문에 도입을 검토했다.

1. 중간에 사용자에게 제작 방식을 고르게 하기
2. 자료 유형에 따라 처리 방식을 정하기

## 판단 기준

| LangGraph가 필요한 신호 | 이 서비스 |
|---|---|
| LLM이 다음 단계를 고른다 | 아니다. 순서는 코드가 정하고 LLM은 "어떤 단어를 가릴지", "어떤 유형인지"만 답한다 |
| 반복 횟수가 정해져 있지 않다 | 아니다. 재시도 1회 뒤 규칙 기반 폴백으로 끝난다 |
| 여러 LLM·도구가 결과를 주고받는다 | 아니다. 페이지당 선택 1회, 문서당 분석 1회다 |
| 중간에 사람의 입력을 받고 재개한다 | 아니다. 방식은 업로드할 때 고른다(ADR-004) |
| 진행 상태를 저장하고 이어서 실행한다 | 필요하다. 다만 Postgres 상태와 Stream 재배달로 해결한다(ADR-001) |

검토한 기능 1은 ADR-004로 중간 선택이 사라졌다. 기능 2는 구조화 출력을 받는 LLM 호출 한 번과 유형별 기본값 표 하나로 끝난다.

## 결정

LangGraph 같은 에이전트 프레임워크를 쓰지 않는다. 파이프라인은 입력·출력이 분명한 함수들을 순서대로 호출하는 평범한 코드로 짠다.

## 결과

- 의존성과 추상화가 하나 줄어든다. 실패했을 때 원인을 추적하기 쉽고, 같은 입력이면 같은 경로를 탄다.
- 설계 원칙 "위치는 코드가, 의미만 LLM이"를 흐름 제어에도 적용한 셈이다. 비용 상한도 코드로 정해진다.

## 재검토 조건

다음 중 하나가 생기면 다시 검토한다.
- LLM이 결과를 보고 스스로 재생성 여부와 방식을 여러 번 정하는 기능
- 사용자와 여러 차례 대화하며 문제 구성을 다듬는 기능
- 서술형 답안을 LLM이 채점하고, 애매하면 근거를 다시 찾아 재판정하는 흐름
