# ADR-009: 웹 프레임워크 — FastAPI

## 상태
채택됨 (2026-10-28)

## 컨텍스트

API 서버와 웹 페이지·이미지 서빙을 맡을 Python 웹 프레임워크가 필요하다(ADR-007: 한 주소로 서빙). 이 서비스에서 중요한 것은 다음과 같다.

- 데이터 계약을 pydantic 모델로 쓰고, API 문서가 거기서 자동으로 나와야 한다. 구현되면 코드가 기준이라는 문서 규칙 4가 이것을 전제로 한다.
- Taskiq 작업 등록, Gemini 호출 등 비동기(asyncio) 코드와 자연스럽게 어울려야 한다.
- 인증 범위는 작다. 가입 없이 로그인만 있고, 계정은 CLI로 만든다(ADR-007).
- 원래 앱(TOEFL 빈칸 앱)이 FastAPI로 되어 있어 골격·정적 서빙·Gemini 클라이언트를 재사용한다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| **FastAPI** | pydantic 모델 → 요청 검증과 OpenAPI 문서가 자동. asyncio 기본. 원래 앱 코드 재사용 | 로그인·세션·CSRF·관리자 화면을 직접 만들어야 함 |
| Django (+ Django Ninja) | 인증·세션·CSRF·마이그레이션·관리자 화면·계정 관리 명령이 기본 제공 | pydantic 계약과 OpenAPI는 Django Ninja를 더해야 함. ORM이 Django 전용이라 `worker`도 Django 설정을 올려야 함. 비동기 지원이 부분적. 원래 앱 코드를 새로 써야 함 |
| Flask | 단순함 | pydantic 검증·OpenAPI·비동기가 모두 추가 작업 |
| Litestar | FastAPI와 비슷한 장점 | 자료와 사용자가 적어 팀이 막혔을 때 찾을 곳이 적음 |

## 결정

FastAPI를 쓴다.

Django가 앞서는 부분은 인증과 관리자 화면이다. 그런데 이 서비스는 가입을 빼서 인증이 로그인 하나뿐이고, 설계의 중심은 데이터 계약과 비동기 작업이다. 그래서 FastAPI의 장점이 더 크다.

## 결과

- 로그인·세션 쿠키·`Origin` 확인과 계정 CLI는 직접 구현한다([데이터 계약](../design/data-contract.md)). 범위가 작아 감수한다.
- 데이터 확인용 관리자 화면이 없다. 필요하면 SQL로 본다.

## 재검토 조건

- 가입·비밀번호 찾기·권한 등급 등 인증 기능이 크게 늘어나면 Django를 다시 검토한다.
