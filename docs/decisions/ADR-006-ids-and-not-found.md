# ADR-006: 식별자와 접근 노출 — 작업 ID = 빈칸 세트 ID, 무작위 UUID, 남의 리소스는 404

## 상태
채택됨 (2026-10-27)

## 컨텍스트

API 초안에는 작업 ID(`GET /jobs/{id}`)와 빈칸 세트 ID(`GET /blank-sets/{id}`)가 따로 있었지만 둘의 관계가 정해져 있지 않았다. 작업 하나는 빈칸 세트 하나를 만들고, 재실행 시 멱등성의 기준도 빈칸 세트 ID다.

자료는 업로더 본인만 볼 수 있다. 따라서 남의 리소스에 접근하는 요청을 어떻게 응답할지도 정해야 한다.

## 검토한 선택지

| 항목 | 선택지 | 장점 | 단점 |
|---|---|---|---|
| 작업과 세트 | **같은 ID** | `jobs` 테이블이 없다. 멱등성 키와 상태 조회 키가 하나다 | 세트를 만들지 않는 다른 종류의 작업이 생기면 다시 나눠야 한다 |
| | 별도 ID | 작업 종류가 늘어도 받아 줄 수 있다 | 지금은 테이블·조회가 하나씩 늘 뿐 쓸 곳이 없다 |
| ID 형식 | **무작위 UUID** | 다른 ID를 추측할 수 없다 | 길고 정렬 순서가 의미 없다 |
| | 순번 정수 | 짧다 | 남의 문서 번호를 추측할 수 있다 |
| 남의 리소스 | **404** | 그 리소스가 존재한다는 사실도 알려 주지 않는다 | 디버깅할 때 "없음"과 "권한 없음"이 구분되지 않는다(서버 로그로 구분) |
| | 403 | 원인이 분명하다 | 존재 여부가 드러난다 |

## 결정

- 작업 ID와 빈칸 세트 ID를 같게 한다. `GET /jobs/{id}`를 없애고 `GET /blank-sets/{id}`가 상태까지 돌려준다.
- 모든 리소스 ID는 무작위 UUID로 한다.
- 없는 리소스와 남의 리소스는 모두 `404 not_found`로 응답하고, 서버 로그에는 둘을 구분해 남긴다.

## 결과

- 상태 조회, 멱등성, 재실행 시 이어서 처리가 모두 세트 ID 하나를 기준으로 한다.
- 세트가 아닌 작업(예: 보관 기간이 지난 파일 정리)이 생기면 Taskiq 작업 이름으로 구분하고, 사용자가 조회할 필요가 없는 작업이면 ID를 노출하지 않는다.
