# 상세 설계서 — 신뢰성(재시도·시간 설정·멱등성·한도)

- 상위 문서: [아키텍처 정의서](../architecture.md) 6장
- 관련 결정: [ADR-001 작업 큐](../decisions/ADR-001-task-queue-taskiq.md)

## 1. 실패 종류별 담당

| 상황 | 담당 | 동작 |
|---|---|---|
| 워커가 처리 중 죽음(배포, 메모리 초과) | RedisStreamBroker의 ack·재배달 | ack가 없으면 `idle_timeout` 후 다른 워커가 넘겨받아 재실행 [확인] |
| Gemini 429(요청 한도 초과)·5xx·타임아웃 | `infra/gemini` | 대기 시간을 점점 늘리며(지수 백오프 + 무작위 지연) 같은 호출을 재시도. 최대 3회 [가설] |
| 위 재시도가 모두 실패, 네트워크 끊김 | `SimpleRetryMiddleware` | `LLMTransientError` 같은 일시적 오류 예외를 던지면 같은 인자로 작업을 다시 보냄. `retry_on_error=True` 라벨이 붙은 작업에만 적용 [확인]. 몇 번까지 다시 할지는 1.1의 `run_count`가 정한다. 재실행 시 끝난 페이지는 건너뛴다(3절 5번) |
| 인증 실패·설정 오류·없는 모델 | 파이프라인 내부 | `LLMPermanentError`. 그 세트의 남은 페이지는 규칙 기반 선택기로 만들고(분석이면 기본 방식) 운영 경보를 즉시 보낸다. 다시 해도 같으므로 재시도하지 않는다. "LLM 장애로 서비스가 멈추지 않는다"는 원칙을 따른다 |
| Gemini 응답이 검증 실패, 응답 불량(`LLMInvalidResponse`) | 파이프라인 내부 | 오류를 붙여 1회 재시도 → 규칙 기반 폴백. **예외를 던지지 않는다**(던지면 미들웨어가 작업 전체를 다시 돌린다) |
| OCR 인식 실패, 잘못된 파일 | 파이프라인 내부 | 상태 `failed` + 사유 기록. 재시도할 의미가 없으므로 예외를 던지지 않음 |
| 자료 분석 실패 | 파이프라인 내부 | 기본 방식으로 진행하고 사유 기록([선택·품질 게이트](selection-and-quality-gate.md) 1절). 예외를 던지지 않음 |
| 품질 게이트 미달 | 파이프라인 내부 | 형식 검증 실패와 같은 경로([선택·품질 게이트](selection-and-quality-gate.md) 2.3). 예외를 던지지 않음 |
| Redis 재시작 | Redis AOF | 대기 중 작업 보존 |

정리하면 **작업이 예외를 던지는 경우는 "다시 하면 될 수도 있는" 일시적 오류뿐**이다.

참고: `SimpleRetryMiddleware`는 "Redis가 죽었을 때 재시도"가 아니라 "작업 실행 중 예외가 났을 때 재시도"다. 워커·Redis 장애 대응은 위 표의 Stream ack와 AOF가 맡는다.

### 1.1 모든 세트를 끝 상태로 보내는 규칙

위 표의 재시도와 재배달은 각자 횟수를 세므로, 그대로 두면 세트가 `running`에 남는 경로가 생긴다. 그래서 **실행 횟수의 기준을 Postgres 하나로 둔다.**

1. 작업을 시작하면 `blank_sets.run_count`를 1 올린다.
2. `run_count`가 상한(4회 [가설]: 첫 실행 + 재시도 2 + 재배달 여유 1)을 넘으면 처리하지 않고 `failed`(`processing_failed`)로 기록한 뒤 ack한다. 매번 워커를 죽이는 PDF가 끝없이 재배달되는 것(독 메시지)을 이 규칙이 끊는다.
3. 일시적 오류(`LLMTransientError`)나 작업 제한 시간 초과가 나면, `run_count`가 상한에 닿았으면 `failed`(`processing_failed`)로 기록하고 정상 종료한다. 아니면 예외를 다시 던져 재시도에 맡긴다. 미들웨어의 재시도 횟수는 이 상한보다 크게 둬서 판단을 Postgres 쪽이 하게 한다.
4. 정리 작업이 `queued`·`running`인 채로 `updated_at`이 30분 [가설] 넘게 멈춘 세트를 찾는다. Redis에서 작업이 사라진 경우(AOF가 저장하기 전의 재시작 등)다. 다시 등록하고, `run_count`가 상한이면 `failed`로 끝낸다. 같은 정리 작업이 DB 행이 없는 원본 파일(저장 뒤 DB 기록에 실패한 업로드)도 지운다.

## 2. 시간 설정 (초기값)

| 설정 | 초기값 | 근거 |
|---|---|---|
| 업로드당 페이지 상한 | 30쪽 | 비용 통제 |
| 업로드 검사 하위 프로세스 | 제한 시간 5초, 메모리 256MB [가설] | API가 쪽수·암호화·JS 포함 여부를 읽을 때 파서를 API 프로세스 안에서 돌리지 않는다(파서 격리) |
| 작업 제한 시간 (Taskiq `timeout` 라벨) | 8분 | 30쪽 처리 시간을 측정한 뒤 조정 |
| `idle_timeout` (RedisStreamBroker) | 15분 | 기본값은 `600000`(밀리초, 10분). 이 시간 동안 ack가 없으면 `XAUTOCLAIM`으로 다른 워커가 넘겨받는다 [확인] |
| Gemini 호출당 타임아웃 | 측정 후 결정 | 응답 지연을 실측한 뒤 정함 |
| 이미지 서명 URL 만료 | 15분 [가설] | 만료되면 프론트가 세트를 다시 조회해 새 URL을 받는다 |

**규칙: 작업 제한 시간 < `idle_timeout`.** `idle_timeout`이 지나면 워커가 살아서 아직 처리 중이어도 작업이 다른 워커에 다시 넘어가 두 번 실행된다(장시간 작업에서 실제로 보고된 사례) [확인]. 30쪽 처리가 8분을 넘는 것으로 측정되면 작업을 페이지 묶음 단위로 쪼갠다.

## 3. 멱등성

Stream 방식은 "최소 한 번 실행"이므로 같은 작업이 두 번 돌 수 있다. 두 번 돌아도 결과가 같게 만든다.

1. 작업 시작 시 Postgres에서 빈칸 세트 상태를 확인하고, 이미 끝 상태(`done`·`partial`·`failed`)면 아무것도 하지 않고 종료(ack).
2. 빈칸·정답 저장은 빈칸 세트 ID 기준 upsert(또는 삭제 후 삽입을 한 트랜잭션으로).
3. 이미지 키를 `blank_sets/{세트 ID}/page_{번호}.webp`처럼 고정해서 덮어써도 무해하게.
4. 모든 저장이 끝난 뒤에 상태를 `done`으로 바꾸고, 그다음 ack.
5. 페이지 하나가 끝날 때마다 그 페이지의 빈칸과 `blank_set_pages` 행을 한 트랜잭션으로 저장한다. 재실행 시 `blank_set_pages`에 행이 있는 페이지는 건너뛴다. 그래서 중복 실행되어도 Gemini는 아직 끝나지 않은 페이지만 부른다.
6. 페이지를 저장하기 전에 문서의 `deleted_at`을 확인한다. 삭제 표시가 있으면 저장하지 않고 `failed`(`document_deleted`)로 기록한 뒤 작업을 끝낸다(ack). 실제 삭제는 정리 작업이 맡는다(실행 주기는 보관 기간과 함께 결정).
7. 자동 모드의 분석 결과(`preset_applied`, `analysis`)는 **페이지를 처리하기 전에** 세트에 저장한다. 재실행 때는 분석을 다시 부르지 않고 저장된 값을 쓴다. 다시 부르면 LLM 결과가 달라져, 앞서 끝난 페이지와 남은 페이지가 서로 다른 방식으로 만들어질 수 있다.

## 4. 결과 백엔드

`RedisAsyncResultBackend`는 디버깅용으로만 쓰고 결과 만료 시간을 설정해 Redis에 결과가 계속 쌓이지 않게 한다(설정 파라미터 이름은 구현 시 확인 [미확인]). 상태 조회 API는 결과 백엔드를 읽지 않는다.

## 5. 한도

순수 판정 함수는 [`cloze/core/usage_limits.py`](../../cloze/core/usage_limits.py)에 구현되어 있다. 호출자가 집계값과 양의 정수 한도를 제공하며, 함수는 환경 변수나 DB를 읽지 않는다. 집계량은 0 이상, 신규 요청 쪽수는 1 이상이어야 하며 bool은 허용하지 않는다. 한도와 같으면 허용하고 초과하면 해당 오류 코드를 반환한다. DB 집계·API·워커 연결과 한도 설정 로딩은 아직 구현되지 않았다.

아래 초기값은 `cloze/config`의 기본값으로 두고 환경 변수로 바꾼다. 수를 세는 곳은 모두 Postgres 조회로 한다. 이 규모에서는 Redis 카운터를 따로 두지 않는다. 동시에 들어온 두 요청이 한도를 한 번 넘길 수 있지만 감수한다.

| 층 | 한도 | 초기값 [가설] | 검사 위치 | 넘으면 |
|---|---|---|---|---|
| 업로드 | 파일 크기, 쪽수 | 20MB, 30쪽 | `api` | `file_too_large`, `too_many_pages` |
| 로그인 | 같은 아이디의 실패 횟수. IP 기준은 Funnel이 실제 접속 IP를 헤더로 넘겨준다는 것이 확인될 때만 더한다(아니면 모든 사용자가 한 IP로 보여 한 사람이 틀리면 전원이 막힘) | 1분에 5회 [가설] | `api`(프로세스 메모리. 인스턴스가 하나라 충분) | `too_many_login_attempts` |
| 사용자 하루 사용량 | 하루 처리 쪽수: 오늘 만든 모든 세트(다시 만들기·실패 포함)의 쪽수 합 + 이번 요청 쪽수 | 300쪽 | `api`(작업 등록 전) | `daily_limit_exceeded` |
| 사용자 동시 작업 | 진행 중(`queued`·`running`) 세트 수 | 2개 | `api` | `too_many_running` |
| 서비스 전체 비용 | 하루 Gemini 호출 수(`llm_calls`의 오늘 기록 + 진행 중 세트의 남은 쪽수 + 이번 요청 쪽수) | 실측 후 결정 | `api`(작업 등록 전) | `service_limit_exceeded`로 거절. 처리 도중에 끊지 않도록 등록 단계에서만 막는다 |
| 폴링 | 클라이언트 조회 간격 | 2초 | `frontend` | — |
| 워커 | 프로세스 하나당 동시 작업 | 1개(늘리려면 워커 컨테이너를 늘림) | `worker` 설정 | 큐에서 대기 |
| 작업 안의 Gemini 호출 | 동시에 보내는 페이지 수 | 4개 | `infra/gemini`(세마포어) | 순서대로 대기 |

### 5.1 발표 설정

발표 때는 청중이 시연 계정 하나를 같이 쓰거나 각자 로그인해 업로드까지 해 본다. 한도가 계정 단위라 그대로 두면 몇 명만 올려도 막히고, 워커가 하나라 대기열이 길어진다. 환경 변수로 아래처럼 바꿔 다시 띄운다.

| 설정 | 평소 | 발표 때 [가설] | 이유 |
|---|---|---|---|
| 사용자 진행 중 세트 | 2 | 20 | 계정을 같이 써도 막히지 않게 |
| 사용자 하루 쪽수 | 300 | 1,000 | 같은 이유 |
| 업로드당 쪽수 상한 | 30 | 5 | 대기열을 짧게. 체험에는 몇 쪽이면 충분 |
| 워커 수 | 1 | 시연 기기 메모리가 허락하는 만큼(2~3) | 동시에 처리 |
| 서비스 전체 하루 Gemini 호출 | 실측 후 결정 | **그대로** | 비용 상한은 발표 때도 유지 |

계정을 같이 쓰면 "내 문서"에 다른 청중의 업로드가 보인다. 발표 때 샘플 PDF만 쓰도록 안내하고, 끝나면 시연 계정을 지운다(`delete-user`로 문서와 세션까지 정리).

**제약:** 동시 호출 상한 4 × 워커 수가 사용하는 Gemini 요금제의 분당 요청 한도(RPM)보다 작아야 한다.

## 6. 남은 확인 사항

| 항목 | 상태 |
|---|---|
| `RedisAsyncResultBackend` 만료 설정 방법 | [미확인] |
| 30쪽 처리 시간 실측 → 작업 제한 시간·`idle_timeout` 조정 | 로드맵 5단계에서 측정 |
| 사용할 Gemini 요금제의 분당 요청 한도(RPM) | [미확인] |
| taskiq 워커의 동시 작업 수 설정 옵션 이름 | [미확인] |
| 한도 초기값(5절) | 스파이크 실측 후 조정 |
