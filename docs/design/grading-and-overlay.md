# 상세 설계서 — 채점·정답 공개·입력칸 표시

- 상위 문서: [아키텍처 정의서](../architecture.md) 3.1
- 관련 문서: [데이터 계약](data-contract.md) 2절(API)·4절(테이블), [선택·품질 게이트](selection-and-quality-gate.md) 2.7(LLM이 낸 변형·힌트 검증)
- 담당: 채점은 서버·워커, 입력칸 표시는 프론트

## 1. 채점

### 1.1 판정 순서

칸마다 위에서부터 차례로 적용하고, 처음 맞는 단계에서 판정을 끝낸다.

| 순서 | 규칙 | 판정 |
|---|---|---|
| 1 | 입력과 정답을 정규화해 비교: 유니코드 NFKC, 대소문자 무시, 앞뒤·연속 공백 정리, 문장부호 제거 | 같으면 `correct` |
| 2 | 검증을 통과한 변형 목록(`variants`, 약어·동의어)과 같은 방식으로 비교 | 같으면 `correct` |
| 3 | `type`이 `number`면 숫자로 바꿔 비교. 허용 오차는 정답의 유효숫자 기준 [가설] | 범위 안이면 `correct` |
| 4 | 편집 거리 1 이내. 정답이 5자 이상일 때만 [가설] | `near`(거의 맞음). 점수에는 넣지 않고 따로 표시 |
| 5 | (후속) 서술·정의형 빈칸만 LLM 판정 | v1에는 없음 |

정답은 선택된 토큰의 원문에서 만든다. LLM이 쓴 정답 문자열은 쓰지 않는다. 한국어는 정답 어절에서 조사를 떼어 낸 형태와 붙은 형태를 모두 `correct`로 인정한다(v1은 어절 단위로 가리므로).

### 1.2 같은 정답이 여러 칸에 있을 때

같은 단어가 여러 칸에 가려졌으면 `answer_group`으로 묶는다. 묶인 칸끼리는 입력을 서로 바꿔 넣어도 맞게 판정한다. 예: 두 칸 모두 "mitochondria"면 어느 칸에 써도 된다.

### 1.3 점수

`score = correct 칸 수 / 전체 칸 수`. `near`는 점수에 넣지 않지만 결과에 따로 보여 준다.

## 2. 정답 공개와 다시 풀기

**제출 횟수와 정답 공개에 제한을 두지 않는다.** 정답을 보고 다시 푸는 것도 복습이라는 판단이다. 같은 칸이 지겨우면 사용자가 원할 때 "다시 만들기"로 다른 빈칸 세트를 만든다.

대신 **모든 시도를 기록하고, 정답을 보기 전의 시도인지 후의 시도인지 구분한다.** 나중에 "처음 풀었을 때 점수"와 "복습 점수"를 따로 꺼내 볼 수 있게 하기 위해서다.

| 기록 | 언제 | 쓰임 |
|---|---|---|
| `attempts.after_reveal` | 시도를 저장할 때, 같은 세트에서 이 사용자가 이미 정답을 봤으면 `true` | 처음 풀이(`false`)와 복습(`true`)을 나눠 보기 |
| `attempts.revealed_at` | 이 시도의 결과 화면에서 정답을 본 시각 | 언제 정답을 봤는지 |

정답 공개(`GET /attempts/{id}/reveal`)는 그 시도를 제출한 뒤라면 언제든 가능하다.

## 3. 입력칸 표시 (빈칸이 이미지에 녹아 보이게)

### 3.1 API로 넘기는 표시 정보

`GET /blank-sets/{id}`의 빈칸마다 `style`을 함께 보낸다. 프론트가 원문과 비슷한 글자 크기·색으로 입력칸을 그리기 위해서다.

| 필드 | 뜻 | 텍스트 PDF | 스캔본 |
|---|---|---|---|
| `style.font_size_ratio` | 글자 크기 ÷ 페이지 폭. 프론트는 `이 값 × 컨테이너 폭`으로 글자 크기를 정한다(창 크기가 바뀌어도 비율 유지) | 토큰의 `font_size` | bbox 높이 × 0.85 [가설] |
| `style.font_color` | 원문 글자색 | 토큰의 `font_color` | 칸 안 어두운 픽셀의 중앙값 |
| `style.bg_color` | 칸 배경색. 가린 자리를 칠한 색과 같다 | 래스터 채우기 때 쓴 색 | 같음 |

`bg_color`는 `core/redact`가 칸을 칠할 때 정한 색을 그대로 넘긴다. 입력칸 배경과 가린 자리가 같은 색이어야 경계가 보이지 않는다.

### 3.2 입력칸 규칙 (프론트)

| 항목 | 규칙 |
|---|---|
| 형태 | 빈칸 하나에 `input` 하나. 글자별 칸은 한글 입력(IME) 조합과 충돌하고 이미지 위에서 어색하다 |
| 위치·크기 | 컨테이너 대비 퍼센트로 `left/top/width/height` 배치. 폭은 `max(bbox 폭, 예상 글자 수 × 평균 글자 폭)` |
| 넘침 | 입력이 길면 오른쪽으로 늘리되 최대 폭을 둔다. 포커스일 때만 그림자와 앞쪽 표시로 이웃 글자를 가리는 것을 알린다 |
| 한글 입력 | 조합 중(`compositionstart`~`compositionend`)에는 Enter·Tab 이동을 막는다 |
| 이동 순서 | Tab·Enter는 빈칸의 `order`(읽는 순서: 줄 → x좌표)를 따른다 |
| 접근성 | `aria-label="페이지 p, 빈칸 n"` |
| 텍스트 출력 | `hint`·정답 등 서버가 준 글자는 HTML로 해석하지 않고 텍스트로만 넣는다 |
| 정답 공개 | 이미지를 다시 받지 않고 오버레이로 정답 글자를 그린다 |

## 4. 남은 확인 사항

| 항목 | 상태 |
|---|---|
| 숫자 허용 오차, `near` 편집 거리 기준 | [가설], 실제 오답 사례로 조정 |
| 스캔본 글자 크기 추정 계수(0.85) | [가설], OCR 단계(로드맵 7) 때 실측 |
| 한국어 조사 분리 규칙(정답 인정 범위) | v1은 어절 기준. 형태소 분석기 도입은 후속 |
